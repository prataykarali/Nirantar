# PortalPulse notices in Nirantar

The Nirantar app now has native red warning, blue action, and green recovery cards. They use the transparent Nira avatar on action and recovery cards. Queue cards come from Nirantar's `fairAccessStore` only after the fair-access API returns a ticket. PortalPulse cards subscribe to `/api/v1/stream/events` only when `VITE_PORTALPULSE_API_URL` is configured, or when this frontend is served by PortalPulse under `/portals/nirantar`.

The two controls are distinct. Nirantar queue cards describe a returned queue ticket and subsequent admission. PortalPulse cards are explicitly labeled **simulator** because the current PortalPulse Nirantar connector acts on its in-process bridge, not on this deployed Nirantar application. An M7 card requires `EXECUTED` and a successful actuation record. A recovery card requires a verified post-action event. The UI does not manufacture events on a timer.

To use the PortalPulse feed in a build, set `VITE_PORTALPULSE_API_URL` to the reachable HTTPS origin of the PortalPulse backend before `npm run build` in `frontend/`. The backend must permit the Nirantar site in CORS and expose a working event stream. To make M7 control the real Nirantar service, replace PortalPulse's local Nirantar bridge with authenticated telemetry and action endpoints on the running Nirantar backend, then verify the resulting behavior with actual requests. Configuring the feed alone does not do that.

The public `bronze-tinsel-n8pb.here.now` publication remains a static frontend. It was rebuilt with `VITE_PORTALPULSE_API_URL=https://portalpulse.antideploy.app`, which sends the fair-access admit and status calls to the PortalPulse-hosted Nirantar prototype bridge. On 2026-10-29, a public browser search under temporary HIGH demand displayed a queue warning, a Nira queue-control notice, and then an admitted notice; the saved search resumed automatically. Demand was restored to NORMAL after the check. This demonstrates the public prototype queue and native notices, not a connection to real railway infrastructure. The rest of Nirantar's API still needs a separate deployed backend for production behavior.
